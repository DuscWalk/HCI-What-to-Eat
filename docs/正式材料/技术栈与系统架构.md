# 技术栈与系统架构

## 一、文档定位与开发范围

本文记录项目已确定的技术选型与架构约定，产品需求以[《产品需求与页面结构》](产品需求与页面结构.md)为准。

**本文是实施方案，不代表下述工程和接口已经实现。** 当前 `main` 以文档为主，已有前端原型保存在 `feature/hubo-prototype-preview` 分支。

本轮仅交付含多平台选择的设计 v2，没有创建工程、schema、迁移、seed 或导入数据；用户无需先实现后台、会话或公共工程才能交付设计。表字段、约束与生命周期以[数据库设计说明](数据库设计说明.md)为准，HTTP DTO、会话、错误与并发以[接口契约](接口契约.md)为准。四人现在可领任务，下述工程与验收是开发任务，不是用户交付前提。

本阶段以固定测试输入、最小 fixtures 与 test doubles 开发以下内部功能闭环，不制作或依赖 seed、导入或真实数据源：

> 浏览商家与菜品 → 条件筛选与推荐 → 管理和比较候选 → 确认选择 → 查看记录。

本阶段不接真实平台数据，不实现真实平台跳转，不实现订单、支付、配送或优惠券核销。候选池不是外卖购物车。

## 二、技术栈

| 部分 | 选型 | 用途 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 页面展示、交互与开发构建，复用已有原型中符合最新需求的部分 |
| 后端运行环境 | Node.js + TypeScript | 与前端统一语言 |
| HTTP 框架 | Fastify | 提供 JSON REST API |
| 数据访问与迁移 | Prisma | 数据库访问、统一模型与版本迁移 |
| 数据库 | SQLite | 降低本地运行成本，满足当前课程项目和模拟数据阶段需要 |
| 用户方式 | 服务端匿名会话 + HttpOnly Cookie | 免注册试用，并隔离不同用户的数据 |
| 测试输入 | 最小 fixtures 与测试替身 | 可复现单元输入，不要求预填全套模拟数据库 |

具体依赖版本在工程初始化时统一锁定。当前不引入微服务、Redis、消息队列、事件总线或通用 Repository 框架。

## 三、整体架构

采用**前后端分离、按业务模块组织的三层后端架构，以模块化单体方式运行**。

```text
React 前端：页面展示与交互
             │ HTTP /api/v1
             ▼
Fastify 后端：一个进程
  Controller 接口层
             ↓
  Service 业务层
             ↓
  数据访问层：Prisma
             ↓
           SQLite
```

这不是传统的服务端 MVC：前端承担 View，后端返回 JSON，不生成页面，也不设置服务端 View 层。

### 3.1 分层职责

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| Controller 接口层 | 注册路由、校验请求格式、取得会话身份、调用 Service、返回 HTTP 响应 | 不编写核心业务规则，不直接操作数据库 |
| Service 业务层 | 推荐规则、候选上限与过期处理、数据归属校验、跨操作事务 | 不依赖 HTTP 请求和响应对象 |
| 数据访问层 | 通过 Prisma 查询和修改数据，封装必要的复杂或重复查询 | 不决定候选替换、推荐筛选等业务政策 |

分层首先是职责约束，不强制每次操作都经过一个仅转发调用的独立文件。简单操作可以由 Service 直接使用 Prisma；复杂或重复查询再提取到模块内部查询文件，不创建没有实际需要的 Repository 抽象。

### 3.2 业务模块

| 模块 | 职责 |
| --- | --- |
| `catalog` | A：逻辑商家/菜品、平台 listing、统一报价解析、浏览、搜索与详情 |
| `recommendation` | A：本次条件、同一报价硬筛选、规则排序、可靠复购与低风险尝新 |
| `candidates` | B：候选增删、平台选择、上限、替换恢复、保留清理、随机与选定入口 |
| `records` | C：选择与候选行为记录、历史查询、记忆修正和推荐可用历史 |
| `profile` | D：匿名会话、可信上下文、长期口味、忌口、分项授权和设置 |

模块间通过明确的业务函数调用，不通过 HTTP 调用自身，不直接修改其他模块负责的业务表。推荐核心逻辑显式接收菜品、条件和用户上下文，便于使用固定输入独立测试。

## 四、工程目录约定

```text
frontend/
backend/
  prisma/
    schema.prisma
    migrations/
  src/
    app.ts
    db.ts
    modules/
      catalog/
        catalog.controller.ts
        catalog.service.ts
        catalog.schemas.ts
        catalog.test.ts
      recommendation/
      candidates/
      records/
      profile/
docs/
```

- 文件按业务模块组织，不把所有业务集中到一个 Controller 或 Service。
- 模块中的 `*.schemas.ts` 定义接口参数和响应校验，不是数据库模型。
- 数据库结构统一定义在 `prisma/schema.prisma`。
- 前后端独立启动，开发环境通过 Vite 代理访问后端，接口统一使用 `/api/v1` 前缀。
- 从旧原型迁入符合最新需求的代码，不直接照搬其下单、支付等超出当前范围的流程。
- A 主责最薄后端模块注册/启动、统一命令及 Prisma 基础接线；D 主责会话、可信上下文、公共校验/错误响应及前端共享请求接线。A+D 对接这些边界，不代写所有公共设施；各人完成自己模块迁移与测试。B/C 可第一天按契约写独立 Service 与测试替身，不等待真实工程接通。

## 五、数据模型与协作约定

### 5.1 v2 九表基线

| 实体 | 作用 | 所属模块 |
| --- | --- | --- |
| `shops`、`dishes` | 商家、菜品与模拟展示信息 | `catalog` |
| `shop_listings`、`dish_listings` | 平台店铺资料与单菜平台报价 | `catalog` |
| `users`、`sessions` | 匿名身份与独立会话表 | `profile` |
| `user_settings` | 每人一条，合并口味、忌口、授权与行为设置 | `profile` |
| `candidates` | 以 user_id+dish_id 复合主键保存菜品候选关系 | `candidates` |
| `records` | 选定、候选未选、模拟曾点过及单条记忆修正 | `records` |

九表字段类型、可空、默认、关系和约束已形成 v2 设计，不代表已建表。平台 MEITUAN/ELEME 为静态映射，不建 platforms 表；逻辑 Shop/Dish 跨平台关联不凭同名合并。费用、ETA、评分从 shops 移至 shop_listings，菜品金额从 dishes 移至 dish_listings，不保留旧单价 fallback。当前不执行实际迁移，不实现外部来源、平台链接或适配配置。不引入 DecisionRound。候选可恢复，餐次、保留时长、恢复资格与重计时由 B 补齐；dishId 与未选时机由 B+C 对齐。

统一约定：金额分、未知 null、API camelCase/DB snake_case、UUID 与 UTC RFC3339 毫秒时间按 v2 执行。A 维护纯函数 resolveDishOffers，所有页面、推荐与候选复用，不能跨平台借配送/ETA或复制公式。DishDTO 使用 offers，无顶层单价；最低仅为 AVAILABLE+COMPLETE 的已知可比最低，无合格者为 null。历史只保存必要名称快照，不存价格快照，按逻辑店铺聚合。数据库接入后是权威来源，前端不另存独立候选/历史事实。

### 5.2 数据库设计和迁移责任

- A（目录与推荐负责人）统一审核模型与迁移；D（个性化与会话负责人）为备份审核人，审核 A 的变更。每人编写自己模块迁移和测试，不由 A 代写全部。
- 模块负责人提交自己的数据需求和实现，不意味着可以独立定义共享字段。
- 全队共用一份 schema 与迁移历史；每人独立本地 SQLite。本期无 seed/导入交付要求；fixtures 仅为最小单元输入，测试可在临时数据库构造最少数据，不要求预填数据库。
- 不提交数据库文件，不共用网络盘上的 SQLite 文件。
- 共享字段或关系修改须同步更新迁移、字段说明、接口契约与相关测试，并由受影响模块确认。
- 涉及数据库结构的变更顺序合并。后合并者先同步主线，调整尚未合并的迁移；已合并迁移不回改，追加新迁移修正。
- 迁移验证至少覆盖空库初始化；结构升级还须验证从上一版本数据库升级成功。

## 六、关键业务与安全边界

### 6.1 选择与记录

候选仍以菜品为粒度，记录页始终按店铺聚合；选定记录粒度由候选与记录模块负责人决定：

- **最终选定：** 当前实现按店铺写入，最终采用店铺级还是菜品级、是否携带菜品由候选与记录模块负责人决定，不由本文拍板；可空 dish_id 已支持两种，不影响表结构。不预设一定选一道菜或多菜，也不代表已下单或已付款。
- **候选未选：** 形成时机由候选与记录模块负责人共同约定，当前待定，不需要用户当下决定。不得各自解释，也不默认确认一家店就把其余候选记为未选。
- **曾点过：** 本阶段由明确标注的模拟历史提供，不从本次选择或浏览推断。

以上是记录类型，不是菜品表上的互斥状态。Record 整体仍可关联菜品，但不要求所有记录都有菜品；同一家店可以在不同选择中产生多条记录。

POST /selections 接收 requestId、shopId、可选 shopListingId（省略/null归一），默认店铺级 SELECTED/USER_ACTION，不从候选猜平台，不要求店已在候选；dishId 由 B+C 后定。B 调 C 同事务原子写入。user+requestId 防重比较 SELECTED、shopId、归一 shopListingId：相同返回原记录，不同（含换平台）409，原记录已删410，并发唯一冲突重读。先匹配重试，再校验新操作的当前平台；显式平台须同店且AVAILABLE，否则按契约404/400/409 OFFER_NOT_SELECTABLE。不指定平台只校验逻辑店。以后同店新平台可用新 requestId，不是终身唯一。不清候选、不判其余未选、不结束轮次。A 使用历史时有 dish_id 就用、没有就退化，缺失关联不得当作新品；历史聚合不因平台拆店。

随机由 B 提供 GET /candidates/random，先归一过期，再从本人 ACTIVE 逻辑菜品候选中均匀抽一道并返回最新 DTO，不按报价数加权、不过滤预算/ETA，无有效报价也不移除候选。除过期归一外不改候选、不自动选定或生成历史，无有效候选返回 null。PATCH /candidates/:dishId 可显式选择同菜 AVAILABLE 且非 INVALID 的 offer 或清为 null；改价/下架保留 chosenListingId，不静默换平台，与派生最低区分。

### 6.2 匿名身份与数据授权

- 服务端生成高熵随机会话凭证，通过 HttpOnly Cookie 保存，数据库保存其摘要与有效期。
- 服务端从会话确定身份，不使用客户端传入的 `userId` 作为授权依据。
- 候选、记录、偏好和设置的读写均校验用户归属。
- Cookie 使用 `SameSite=Lax`，HTTPS 环境启用 `Secure`；写接口校验请求来源。
- 历史、口味等授权由服务端业务逻辑执行，不能仅隐藏前端控件。
- 不实现注册、账户恢复或跨设备同步；清除 Cookie、会话失效或更换设备后不保证找回原记录。

## 七、开发与验收原则

本设计可供四人直接领任务。各模块先用固定测试输入、最小 fixtures 和测试替身独立开发，不等待数据源或公共工程交付；不要求用户实现后端、session、迁移或 seed。工程接线按分工推进，替身通过不等于实际接口或最终联调完成。

尽早集成最短闭环，不把接线推迟到全部开发结束。首阶段验收要求：

1. 开发后按统一命令启动前后端，从空库完成迁移，不要求 seed 或导入。
2. 各成员遵守相同 schema/DTO，空库目录 API 正常返回空集合；空数据不能证明推荐质量。
3. 跑通浏览、推荐、候选比较、确认选择与查看记录。
4. 验证用户隔离、推荐硬筛选、候选上限、恢复与过期处理、本人有效候选随机抽取、重复确认及授权关闭；恢复规则未配置时验证能力位与409 CANDIDATE_POLICY_PENDING。
5. 全流程不依赖真实平台数据、真实跳转或支付服务。
6. 覆盖单平台报价、便宜慢/贵快不可跨报价拼合、全未知价最低null、chosen下架不丢候选、错菜offer拒绝、同request换平台409、多offer不增加候选数或随机权重、平台记录仍按同一逻辑店聚合。测试可临时构造最少数据，最终跨模块验收须真实接通，不能以替身通过替代。

推荐数量、候选上限等技术默认与范围见 v2 规格；降低上限不删已有候选，关闭授权不删数据但停止推荐使用。餐次边界、expires_at 生成、保留优先级、恢复资格与重计时由 B 补齐，未配置时能力位 false，相关配置/恢复409 CANDIDATE_POLICY_PENDING。候选可恢复，PUT 对已删/到期关系要求走恢复入口，替换受同样约束；B+C 对齐 dishId 与未选时机，不阻塞其他模块。候选计数/状态写入及上限设置更新须先在 SQLite 写事务取写锁后检查，忙时有界重试整个事务，不用进程锁冒充跨连接安全。
