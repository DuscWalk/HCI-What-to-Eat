# 四人开发分工

## 一、分工依据与设计交付

按四个主页面垂直分工，姓名暂用 A—D；每人交付页面交互、对应后端业务与接口、测试及联调，不是前后端拆人。本方案不宣称工作量均衡，依赖和公共事务应单独协调。

已核对[产品需求与页面结构](产品需求与页面结构.md)、[技术栈与系统架构](技术栈与系统架构.md)、[数据库设计说明](数据库设计说明.md)、[接口契约](接口契约.md)。字段、DTO、默认值、范围、错误码、分页和校验以 v2 数据库说明与接口契约为权威，不自行增加字段或业务定值。权威人员映射为 A 首页/catalog/recommendation、B 候选/selections/random、C 记录、D 个性化/profile/session。

**现在可按文档领任务开发。** 用户交付仅为设计，不需先实现工程、后端接口、迁移、session 或数据初始化。公共基础尚未实现是开发任务，不是用户补交前提。A+D 按下述职责接线，B/C 第一天即可用独立 Service、固定测试输入和 test doubles 开始；替身通过不等于实际接口或最终集成完成。

本期不制作或依赖 seed、导入、实际商家菜品来源、真实平台链接、订单、支付、配送或优惠券系统。多平台选择现在进入设计，不等于已接真实平台；只使用最小单元 fixtures/固定测试输入，必要时在临时测试数据库构造最少数据，不交付全套模拟库。平台去向仅作模拟反馈，优惠为单菜该平台模拟已适用优惠。

### 统一业务边界

- **随机抽取归 B：从当前用户的当前有效候选中抽一个，放在候选页，只给建议，不自动选定、不生成历史。** 不从全目录或“符合本次条件的菜品”抽取，不自动加候选。空有效候选时明确展示无可抽取项，不产生写入。首页快捷入口留待办，不交给 A 实现另一套算法。
- 随机由候选模块提供 `GET /candidates/random`，从本人当前有效候选中均匀抽取，无请求体、无 conditions。
- 候选仍按逻辑菜品计数，不按平台报价计数；默认选定为店铺级，可选平台，是否携带 dishId 由 B+C 后定；不因选定清空候选或把其他候选记未选，不引入决策轮次。

## 二、逐人任务与验收

建议前端在 `frontend/` 按页面/功能分目录，后端沿用 `backend/src/modules/`；这些是开发目标，不声称骨架已存在。每人交付页面、对应 Controller/Service/schema、本模块迁移、契约样例、测试及简短启动/验收步骤；跨模块通过业务函数，不 HTTP 调自己，不直接改其他模块业务表。

### A：首页、本次条件/推荐弹窗、规则推荐

- **任务与模块：** 首页浏览、条件/推荐弹窗、加入候选；负责 catalog/recommendation、逻辑 Shop/Dish 与 shop_listings/dish_listings、统一静态平台映射和纯函数 resolveDishOffers。维护完整 offers DTO、同一报价同时满足预算/ETA、已知可比最低及匹配最低，不留旧单价 fallback。主责最薄后端模块注册/启动、统一命令和 Prisma 基础接线，与 D 对接，不包办全部公共设施或其他人的迁移。
- **接口与交付：** `GET /shops`、`GET /shops/:id`、`GET /dishes`、`GET /dishes/:id`、`POST /recommendations`；独立报价解析与推荐核心测试。显式接收目录/listing、有效条件与可信上下文；新增平台同步 schema/API 映射，不做真实平台采集/链接。
- **验收：** 用固定样例查询目录，空目录正常展示；条件可跳过；预算/距离/送达时间/忌口及未知资料按契约筛除，口味匹配和本次条件覆盖/合并遵守契约；结果按店分组，不足不硬凑。推荐不写候选或记录；点击加入调用 B 后，候选查询能看到同一菜品。关闭历史或口味授权后，以测试证明不再装载/使用相应保存数据；弹窗可关闭且不误触背景。
- **排除：** 不维护第二套候选、不代写记录/设置，不负责随机抽取、机器学习或长文字推荐理由。复购不冒充真实订单；低风险资料不足不虚构结果。
- **报价验收：** 单平台正常；便宜慢与贵快不能拼合通过；全未知价最低为null；INVALID单条隔离而非整列表500；推荐每道菜给出非空 matchingOfferIds 及正确 lowestMatchingOfferId。空库返回空集合，不能据此声称推荐质量已验证。

### B：候选页、候选生命周期、店铺选定、随机抽取

- **任务与模块：** 候选展示/比较 A 返回的 offers、最低与显式 chosen 区分、未知价格提示、增删/上限/替换/清空、过期与恢复、随机及选定入口。负责 candidates 和 selections，PATCH chosenListingId 仅改选择及 updatedAt；报价改价/下架保留候选与选择，不静默换平台。
- **接口与交付：** 契约中的 `/candidates` 全组操作（含 `GET /candidates/random`）和 `POST /selections`；提供给 A 的加入函数、给 D 的清空及上限协调函数、给 C 的行为协作入口。选定调用 C 的记录函数并传同一事务，不跨模块直接写 records。
- **验收：** 重复加入 ACTIVE 原样返回且不刷新时间；超限新增失败，满额替换成功且失败整体回滚；降低上限不删旧候选。过期读取先归一；当前保留/恢复未配置时能力位为 false，恢复及非空保留设置按契约返回 409 CANDIDATE_POLICY_PENDING，不能假成功。随机样例含其他用户、已删/过期和目录中未入候选的菜品，结果只能来自本人有效候选，抽取前后候选和记录不变；空集合可观察地提示无结果。
- **选定验收：** 一次一店，可连续确认不同店；店不必已在候选；同次重试复用 requestId，返回原记录，不同 payload 为 409、原记录软删为 410；并发重试不重复写、不泄漏为 500。选定后候选保持原状，不生成其他候选未选记录。测试覆盖事务失败回滚。
- **平台验收：** 选择别道菜的 offer 返回400，非AVAILABLE/INVALID返回409 OFFER_NOT_SELECTABLE；下架不丢 chosen 或候选。选定可省略平台，不从候选猜；同request换平台409，成功操作下架后重试仍返回原记录。多offer不增加候选计数或随机权重；无有效报价的ACTIVE菜仍参与随机。
- **排除：** 不以随机结果自动确认，不推断已下单，不代 C 决定未选形成时机；不擅自定义餐次、恢复资格或重计时规则。

### C：记录页与记录管理

- **任务与模块：** 店铺级历史聚合、单条记录查询、类型区分、记忆原因修正、推荐使用开关、单条软删除及模拟去向反馈。负责 `records`，前端建议记录列表与编辑归 C。
- **接口与交付：** `GET /records/shops`、`GET /records`、`PATCH /records/:id`、`DELETE /records/:id`；给 B 事务内记录函数，落实可空 shopListingId、菜店/平台店一致、防重、名称快照和软删；给 A 可用于推荐的历史。MOCK_HISTORY 仅用最小测试输入表达，不要求seed或开放任意创建历史接口。
- **验收：** 用固定多店、多类型样例核对聚合、排序、分页及类型筛选，类型筛选不错误截断该店其他类型计数。修正后重查生效；禁止推荐使用的记录仍展示/计数但不进入推荐历史；软删后不展示、不聚合、不用于推荐，重复删除按契约处理，防重标识仍保留。不同会话无法读写对方记录；B 连续确认多家后各自可见，不把 SELECTED 显示为真实曾点过。
- **排除：** 不接真实订单，不做物理擦除承诺，不代 D 管总授权，不独自推断候选未选；记录页锁定店铺如需选定，调用 B 的选定入口，不另写一套流程。
- **平台与证据验收：** 引用不同平台的记录仍聚合为同一逻辑 shop；RecordDTO 返回关联平台码，不增加价格快照。与 B 对齐是否写 dishId；有菜品关联才作菜品级证据，缺失不得当新品。

### D：个性化页、偏好/授权/设置

- **任务与模块：** 个性化页、偏好/授权/设置、profile/session；主责会话、可信上下文、公共校验/错误响应及前端共享请求接线，与 A 对接。公共基础由开发中逐步实现，不是用户先交付或其他人开始独立 Service/测试的前提。
- **接口与交付：** `POST /session`、`GET /me/settings`、`PATCH /me/settings`；服务端身份/设置读取能力及授权上下文供 A/B/C 调用。手动清空调用 B，不在 profile 直接更新候选表；上限更新与 B 共用符合契约的写事务流程。
- **验收：** 新会话默认值与契约一致，有效会话复用不延期；表单叶字段合并、数组替换、未知字段/错误值拒绝。保存后重查一致，推荐数量/弹窗设置由 A 使用，随机显隐由 B 使用；降低上限不删候选。关闭授权不删数据但服务端后续推荐不使用对应数据；健康目标授权不扩展为未定义的健康目标字段。保留规则未配置时不提供假可用设置。
- **隔离验收与排除：** 两个 Cookie 会话的设置互不可见；客户端自报 userId 不能授权，写请求 Origin、Cookie 和失效行为按契约验证。不做注册、账户恢复/跨设备同步，不代其他模块维护业务状态。

## 三、简明交接矩阵

调用方负责正确传参、处理成功/失败并更新页面；接收方负责本模块规则、归属校验、稳定返回与测试。双方共同验证实际调用，不能只交一个空函数或只画页面。

| 调用方 → 接收方 | 交接内容 | 接收方责任 |
| --- | --- | --- |
| A → B | 首页/推荐加入候选 | 去重、上限、状态与事务；返回权威结果，失败不造成前端假加入 |
| A → C / D | 可用历史 / 设置与授权上下文 | C 排除已删和单条禁用；D 提供可信设置/授权；A 在总授权关闭时不装载历史、不使用未授权偏好 |
| B → A | 逻辑目录、offers及统一报价解析 | A 提供 resolveDishOffers；B 不读旧价或复制公式，不把单菜估价相加称整单 |
| B → C | 每店选定记录，同一事务 | C 落实记录快照、防重及软删语义；B 负责入口及事务编排，失败共同回滚 |
| C → B | 记录页若触发店铺确认 | B 复用选定入口；C 不绕过 requestId 防重自行插记录 |
| D → B | 手动清空、影响上限的设置更新 | B 提供候选规则/事务协作；D 在同一受保护流程写设置，不留计数竞争窗口 |
| A / B → D | 推荐行为设置、随机显隐及会话 | D 返回本人配置；A/B 消费最新权威值，不另存相冲突默认值 |
| B ↔ C | 候选未选形成时机 | 先共同确认再实现，明确写入触发、重复防护及记录独立生命周期；当前不自动生成 |

所有私有操作从会话确定身份并限定用户归属；公共目录不因此变为用户私有。前端不以 localStorage 再维护独立候选/历史权威状态。可延后普通页面跳转与刷新体验，但不能延后写入失败回退、重复提交防重和跨模块数据一致性。

## 四、并行开发、最早联调与公共约束

1. **按设计直接领任务：** 每人用固定测试输入、最小 fixtures 与同契约测试替身开发成功/失败/空集合，不依赖数据源或预填数据库。A 做最薄启动/注册/Prisma接线，D 做会话/校验错误/共享请求；B/C 可第一天独立开发。随机按 GET /candidates/random，不自造其他字段。
2. **最早主流程联调：** 不等四页做完，先串起 D 建会话 → A 浏览/推荐 → B 加入候选并查询 → B 按店确认、C 写记录 → C 查询显示。随后接 D 设置/授权即时影响 A/B、B 随机只建议、记录修正影响推荐；再补替换/清空/未配置能力和错误反馈。
3. **共同可执行检查：** 各自留下可运行测试命令和固定复现步骤；集成至少跑双会话隔离、Origin 校验、候选并发增量与降低上限竞争、替换失败回滚、选定并发重试、授权关闭及空数据。候选计数/状态写入与上限更新先在 SQLite 写事务取得写锁，再归一过期、读配置、计数、校验和写入；忙时有界重试整个事务，耗尽按契约返回 503，不拿进程锁代替跨连接保证，Prisma 锁方式须实际验证。
4. **迁移沿用既有约定：** 各人写自己模块迁移与测试，A 审核统一模型/迁移，D 备份审核，A 的变更由 D 审核。共用 schema 与迁移历史，各人独立本地 SQLite，不提交数据库文件；不制作/依赖seed或导入。结构变更顺序合并，后合并者先同步主线；已合并迁移不回改。共享变更同步字段说明、接口和测试；验证空库初始化，升级验证上一版迁移。测试可在临时库构造最少数据，不视为用户交付seed。
5. **阶段完成分开判断：** 文档已能领任务不等于接口已实现；独立测试/替身通过不等于最终联调。实际跨模块、真实数据库事务与双会话流程接通后才验收集成；空库正常空返回不能证明推荐质量。

## 五、未定项与所有者

| 项目 | 所有者与处理边界 |
| --- | --- |
| 随机接口与测试 | B 按 GET /candidates/random 契约实现本人有效候选抽取，A/D 确认目录、设置依赖 |
| 候选保留、餐次、恢复资格与重计时 | B 牵头，C 确认记录影响、D 确认配置；未定前保持契约能力位 false、对应 409，不默认永久保留或假恢复 |
