# 数据库设计说明 v2

## 一、状态与统一约定

本文是包含多平台选择的 **v2 数据设计基线**，不是数据库已经落地的证明。用户本次交付的是设计说明，无需先实现工程、接口、迁移、会话或数据初始化；四人可据此领任务，使用固定测试输入与测试替身并行开发。本期不制作或依赖 seed、导入或真实数据源。业务依据见[产品需求与页面结构](产品需求与页面结构.md)，工程边界见[技术栈与系统架构](技术栈与系统架构.md)，API 权威规格见[接口契约](接口契约.md)。随机与 PRD 一致，从调用者当前有效菜品候选中抽取。

- Fastify + TypeScript + Prisma + SQLite；数据库表和列使用 snake_case，Prisma 属性及 JSON API 使用 camelCase，通过映射对应。
- 标识使用服务端生成的 UUID 字符串；`records.request_id` 由客户端生成 UUID。除该请求标识外，不接受客户端自报用户归属。
- 下表 `String` 对应 SQLite TEXT，`Int` 对应 INTEGER（Prisma 32 位有符号整数范围），`Boolean` 由 Prisma 映射，`DateTime` 由 Prisma 处理。API 时间统一为 UTC RFC3339 毫秒格式，例如 `2026-11-25T08:00:00.000Z`。
- 金额为整数分，`null` 表示未知，不等同于 0。非空字符串不得仅含空白。所有 `_json` 字段为 String/TEXT，经统一 schema 校验固定形状，API 解析为对象或数组，不输出 JSON 字符串。
- 表中“无默认”表示调用方必须明确提供；时间 `now` 由服务端统一取值，更新时间由 Prisma/Service 维护，不声称有数据库触发器。外键均启用 SQLite 外键校验，标识不可修改，更新行为 Restrict。
- PK、FK、UNIQUE、索引应在后续开发迁移中真实落实。范围、字符串集合和跨字段条件不能仅靠 TypeScript 类型或 Prisma enum 宣称数据库已约束：支持的 CHECK 由迁移落实；其余由 Service 在事务内验证。实施时须验证实际约束，不能只写在文档里。
- 平台代码为 MEITUAN / ELEME，使用统一静态映射，不建 platforms 表；新增平台须同步 schema 校验与 API 映射。逻辑 Shop/Dish 表示跨平台同一对象，不凭名称相同自动合并。不增加 externalId、平台 URL 或适配配置，不承诺外部接入已完成。

### 2.6 candidates：用户与菜品的当前候选关系

| 字段 | Prisma 类型 | 可空 | 默认 | 含义与约束 |
| --- | --- | --- | --- | --- |
| user_id | String | 否 | 无 | FK → users.id，删除 Cascade；复合 PK 一部分 |
| dish_id | String | 否 | 无 | FK → dishes.id，删除 Restrict；复合 PK 一部分 |
| chosen_listing_id | String | 是 | null | 显式选择的 dish_listings.id；复合 FK 见下文 |
| status | String | 否 | ACTIVE | ACTIVE / DELETED / EXPIRED |
| created_at | DateTime | 否 | now | 首次关系创建时间，不重建关系 |
| updated_at | DateTime | 否 | now | 最近修改时间 |
| status_changed_at | DateTime | 否 | now | 最近状态转换时间 |
| expires_at | DateTime | 是 | null | 未配置到期规则时为空，不是永久保留承诺 |
| removal_reason | String | 是 | null | USER / CLEAR / REPLACED；仅区分移除方式，仅 DELETED 可非空，DELETED 必须有原因 |

PK(user_id, dish_id) 技术去重；索引(user_id, status, created_at)、(status, expires_at)、(chosen_listing_id, dish_id)。复合 FK(chosen_listing_id, dish_id) → dish_listings(id, dish_id)，删除/更新 Restrict，保证选择属于同一道菜。ACTIVE/EXPIRED 的 removal_reason 必须为空。

chosen_listing_id=null 表示没有显式平台选择，不是已自动选择最低价；最低可比报价只是派生展示。删除、到期不清除此字段；报价改价或下架保留选择和候选，不静默换平台。只改显式选择时仅更新 updated_at，不改 created_at、status_changed_at、expires_at，不生成历史。

- ACTIVE 重复加入返回原行，不刷新任何时间、不重新计数。PUT 对 DELETED/EXPIRED 返回409 CANDIDATE_STATE_CONFLICT，要求走恢复入口；替换目标已删/到期时受同样恢复资格约束。
- 保留原行用于去重与恢复，DELETED/EXPIRED 可恢复复用原行。恢复资格、是否重新计时与保留规则由候选模块负责人补齐，未配置返回409 CANDIDATE_POLICY_PENDING。
- 读取/计数前将 `expires_at <= now` 的 ACTIVE 归一为 EXPIRED，同时更新状态时间、更新时间并清空移除原因；null 暂不清理。
- retentionConfigured/restoreConfigured 表示对应规则是否配置，当前均为 false。canRestore 由服务端计算：ACTIVE 为 false/NOT_RESTORABLE；非ACTIVE且恢复规则未配置时为 false/POLICY_PENDING，恢复接口返回409 CANDIDATE_POLICY_PENDING，不假成功。配置后按资格与上限判断，具体错误和能力值见接口契约。

### 2.7 records：单条行为与记忆记录

| 字段 | Prisma 类型 | 可空 | 默认 | 含义与约束 |
| --- | --- | --- | --- | --- |
| id | String | 否 | 服务端 UUID | PK |
| user_id | String | 否 | 无 | FK → users.id，删除 Cascade |
| request_id | String | 否 | 无 | 客户端 UUID；内部模拟历史也须提供稳定操作 UUID |
| shop_id | String | 否 | 无 | FK → shops.id，删除 Restrict |
| dish_id | String | 是 | null | 可选菜品，复合 FK 见下文 |
| shop_listing_id | String | 是 | null | 可选平台店铺关联，复合 FK → shop_listings(id, shop_id)，删除/更新 Restrict |
| kind | String | 否 | 无 | SELECTED / CANDIDATE_NOT_SELECTED / PREVIOUSLY_ORDERED |
| source | String | 否 | 无 | USER_ACTION / MOCK_HISTORY |
| occurred_at | DateTime | 否 | 无 | 行为发生时间；选定使用服务端 now |
| shop_name_snapshot | String | 否 | 无 | 当时店名，非空且<=100字符 |
| dish_name_snapshot | String | 是 | null | 当时菜名，非空时<=100字符 |
| reason | String | 是 | null | 单条记忆原因，最多200字符；null 清除 |
| use_for_recommendation | Boolean | 否 | true | 是否允许该条用于推荐，仍受总授权约束 |
| created_at | DateTime | 否 | now | 写入时间 |
| updated_at | DateTime | 否 | now | 最近修正时间 |
| deleted_at | DateTime | 是 | null | 软删除时间 |

UNIQUE(user_id, request_id)；复合 FK(dish_id, shop_id) → dishes(id, shop_id)，删除 Restrict，保证有菜品时菜店匹配。dish_id 为空时 dish_name_snapshot 必须为空；有菜品时必须保存菜名快照。索引(user_id, deleted_at, occurred_at DESC, id DESC)、(user_id, shop_id, deleted_at, occurred_at DESC)、(shop_listing_id, shop_id)。平台码从不可换绑的 shop_listing_id 关联派生，不另存重复平台码或价格快照。

- SELECTED 的 source=USER_ACTION，默认仍是店铺级，可携带平台店铺关联，不代表已下单。是否携带菜品及最终记录粒度由 B（候选）与 C（记录）决定，字段已支持两种；不限制同店以后再次选定，聚合仍按逻辑店铺，不因平台拆店。
- PREVIOUSLY_ORDERED 仅允许 source=MOCK_HISTORY；CANDIDATE_NOT_SELECTED 为站内行为，source=USER_ACTION，但写入时机由候选与记录模块负责人共同约定，当前不自动产生。不是确认一家就将其余判未选。
- 相同 user+requestId、同 SELECTED、同 shop_id 和归一后的 shop_listing_id（省略/null均为空）是同次重试，返回原记录，不改发生时间或快照；不同 payload（含换平台）返回409 REQUEST_ID_REUSED。原记录已删则返回410 RECORD_DELETED，不复活。先匹配重试，再检查新操作的当前平台可用性，避免已成功操作因下架而无法重试。新一次选同店或新平台使用新 requestId。
- 删除只软删一条，排除展示、聚合与推荐，保留请求防重。不承诺物理擦除；用户外键 Cascade 是身份物理删除的结构行为，不是已提供账户删除 API。

**历史证据能力：** 记录页始终按店铺聚合，不受选定记录粒度影响。店铺级 SELECTED 不证明某道菜吃过；推荐模块必须“有 dish_id 就用、没有就退化”，仅有菜品关联才可作菜品级判断，不得把缺失关联当作新品。dish_id 是否写入由候选与记录模块负责人决定，可空字段已支持，不影响表结构。

## 三、固定 JSON 形状与报价

以下为沿用的技术默认，不是用户验证后的业务结论；JSON 对象拒绝未知字段。标签数组最多20项，每项去空白后非空、<=32字符，规范化后去重。

```json
{
  "preferences": {"tasteTags": [], "avoidTags": []},
  "consents": {"history": false, "taste": false, "healthGoal": false},
  "settings": {
    "candidateLimit": 5,
    "recommendationCount": 3,
    "autoPopupAfterSeconds": null,
    "showRandom": true,
    "candidateRetention": null
  }
}
```

- candidateLimit 整数1..20；recommendationCount 整数1..5，按店数计；autoPopupAfterSeconds 为 null 或整数10..3600；其余授权与显隐为 Boolean。
- candidateRetention 当前只接受 null，表示规则未配置；非空 PATCH 返回409 CANDIDATE_POLICY_PENDING，不宣称餐次清理已实现。
- PATCH 按叶字段合并，数组整体替换，不接受其他 null。降低上限保留已有候选，只阻止新增导致超限；满额替换不增数量仍允许。关闭授权不删数据，但后续推荐不再使用对应保存数据。
- OfferDTO 与 PriceEstimate 具体字段见接口契约。A 维护纯函数 `resolveDishOffers({dish,shopListings,dishListings,offerConditions?})`，输出 offers、lowestComparableOfferId、matchingOfferIds、lowestMatchingOfferId；estimatePrice 可作内部计算。每个报价只取自身菜品价/包装/优惠及所属平台店铺配送，统一计算 `菜品+包装+配送-优惠`，禁止跨平台借费用或 ETA。四项全部已知且正确为 COMPLETE；缺项为 INCOMPLETE、totalCents=null；完整金额关系错误或越界为 INVALID、price=null，issue为 DISCOUNT_EXCEEDS_SUBTOTAL / PRICE_OUT_OF_RANGE，不返回负数或夹零。受控写入拒绝错误报价，运行时隔离单条坏报价并服务端诊断，不使整列表500；真正异常仍500。
- 有效 availability：任一侧 UNAVAILABLE 则 UNAVAILABLE，双方 AVAILABLE 才 AVAILABLE，其余 UNKNOWN。最低仅比较 AVAILABLE+COMPLETE 报价，按 total 升序、ETA 升序（未知末）、platformCode 升序、id 升序；无合格者最低id为null，只表示已知可比最低，不断言未知报价更贵。缺平台不补造报价。
- 所有报价级条件须在同一个 AVAILABLE 且非 INVALID 的报价上同时满足；预算/ETA 有要求则相应值须已知。便宜但慢与贵但快不能拼成“便宜又快”。未设预算可匹配缺价报价，但不得称其最低；lowestMatchingOfferId 仅在匹配的完整报价中取。其他模块与前端不得读取旧价或复制计算。
- 当前仅单菜 CNY 模拟估价，不可相加当多菜整单，不建 Coupon，不存价格快照。仅保存必要店名、菜名快照。

## 四、关系、分表与不落库信息

```text
shops 1 ── N dishes
shops 1 ── N shop_listings
dishes 1 ── N dish_listings N ── 1 shop_listings（菜店一致）
users 1 ── N sessions
users 1 ── 1 user_settings
users 1 ── N candidates N ── 1 dishes
                       └── 可选 chosen_listing_id → dish_listings（同菜）
users 1 ── N records N ── 1 shops
                       └── 可选关联 dishes（菜店一致）
                       └── 可选关联 shop_listings（同店）
```

Shop/Dish 是跨平台逻辑对象，listing 分离平台费用、时效、质量与报价，避免双源和跨平台混算。Candidate 表示用户与逻辑菜品关系，多个报价不增加候选数量或随机权重；随机先均匀抽 ACTIVE 菜品，再取最新 DTO，即使无有效报价也不默默移除候选。Record 生命周期独立于候选清理，按逻辑店铺聚合，不因引用不同平台而拆店。偏好、授权、设置合并一条，Session 是安全技术表。

不保存本次条件、随机结果、推荐分数、当前候选计数、熟店标记或最低报价缓存；它们来自请求或派生计算。不建 DecisionRound、platforms、tags 关联表、券、订单、支付或重复 selection 表，不引入真实数据接入。选定不清候选、不结束轮次。

## 五、事务、并发与责任边界

- 候选模块调用记录模块的函数并共用事务，确认写入原子、防重复。并发 UNIQUE 冲突后按 user+requestId 重读并核对 payload，不直接报500；已软删也参与防重。
- 候选上限检查、状态变更与影响上限的设置更新使用 SQLite 写事务，先取得写锁，再归一过期、读取 ACTIVE 数与配置、校验并写入。不能先在事务外计数，不能用进程锁冒充跨连接安全。替换失败整体回滚。
- 数据库忙时有界重试整个事务，耗尽返回503 DATABASE_BUSY。具体事务获取写锁方式在实施时验证，不预写未经确认的 Prisma 锁 API。
- 所有私有查询同时限定会话 user_id；记录模块提供推荐历史时只提供未删除且 use_for_recommendation=true 的记录，总 history 授权关闭时由服务端不装载历史。

## 六、仍需实现负责人处理的规则与变更边界

餐次边界、expires_at 生成、保留时长优先级、恢复资格与是否重新计时由 B（候选）补齐；选定记录粒度、是否写入 dish_id 与未选记录时机由 B+C（候选与记录）共同约定。这些不是要求用户逐项拍板的开工阻塞；规则未配置时按能力位与409 CANDIDATE_POLICY_PENDING 工作，其他目录、设置、记录与推荐可并行。

内部可调：不改变契约含义的推荐权重、排序启发式、数据库重试次数及退避参数。新增保留策略须同步能力与配置 schema，不能私改 null 含义。字段类型/可空性、状态、唯一键、删除语义、价格公式、授权作用、排序分页、requestId 幂等和错误码属于共享契约，变更须由受影响模块确认并同步迁移、接口、文档与测试。技术默认值变更也应同步初始化和接口样例，不擅自改已有用户配置。

加入后停留/跳页、入口位置、普通列表刷新仍可延后处理，不在此定设计；若影响重复写入或跨模块状态才升级为契约事项。
